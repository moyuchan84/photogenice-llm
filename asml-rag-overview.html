INTERNAL ARCHITECTURE REVIEW

ASML 설비 로그 RAG 시스템
아키텍처 논의 자료

설비 로그(DB 적재분) 및 실시간 API 데이터를 기반으로, 판정·원인분석을 자동화하는 RAG 시스템의 전체 구조와 5개 기능 확장안을 정리했습니다.

00개요

PostgreSQL(+pgvector)에 적재된 설비 로그와, 부서 API로부터 받는 실측·스펙 데이터를 결합해 과거 이력 기반 판정(History), 스펙 in/out 판정(Focal Curve · Final XY), 에러 원인 추정(ID Dump) 4개 기능을 하나의 RAG 코어로 서비스합니다.

PRINCIPLE 01

판정과 설명의 분리

숫자 비교(스펙 in/out)는 결정론적 코드로만 계산하고, LLM은 근거를 바탕으로 원인·결론을 설명하는 역할만 담당합니다.

PRINCIPLE 02

1개 RAG 코어 + Feature Registry

기능별 개별 LLM을 두지 않고, 검색·프롬프트·판정 로직을 공유하는 코어 위에 기능별 설정만 등록합니다.

PRINCIPLE 03

결정론 우선, 에이전트는 부가 레이어

MCP/tool-calling 기반 에이전트는 판정 파이프라인을 대체하지 않고, 엔지니어용 탐색 인터페이스로만 별도 운용합니다.

02호출 흐름 — 판정 경로 vs 탐색 경로

판정을 반환하는 핵심 경로와, 엔지니어가 자유롭게 파고드는 탐색 경로는 서로 다른 신뢰도 요구사항을 가지므로 흐름을 분리합니다.

핵심 · 결정론적
  1. 요청 수신 — inline 데이터(프론트 렌더링값) 또는 identifier(설비/기간)
  2. 데이터 확보 — inline이 없으면 ASML API 호출 또는 DB 조회
  3. 판정 계산 — Evaluator가 spec in/out 또는 결정론적 비교 수행 (LLM 미사용)
  4. 조건부 RAG — OUT_OF_SPEC/근접 시에만 벡터 검색 실행
  5. LLM 설명 생성 — 판정 결과 + 검색된 과거 사례 → 원인/권고 JSON 생성
  6. 저장 — spec_evaluations / judgements에 근거와 함께 기록
선택 · 에이전트(MCP)
  1. 자유 질의 수신 — "왜 이렇게 나왔는지", "비슷한 케이스 더" 등
  2. LLM이 필요한 툴 선택 — get_spec_evaluation / search_historical_cases 등
  3. 툴 실행 — 이미 계산·저장된 결과만 조회 (재계산 없음)
  4. 결과 종합 — LLM이 여러 툴 결과를 조합해 자연어로 응답
  5. 후속 질의 반복 — 대화형으로 계속 탐색 가능

03Vector DB 구조화

구조화 컬럼(설비/기간/에러코드/기능유형)과 벡터 유사도를 함께 쓰는 하이브리드 검색을 기본으로 합니다. 로그는 문맥이 짧아 한 줄 단위가 아닌 세션/에러 윈도우 단위 청킹을 사용합니다.

청킹 전략

동일 설비 기준 시간 간격 내 로그를 하나의 이벤트 버스트로 묶고, 에러/경고 발생 시점 전후 로그를 함께 포함해 인과관계를 임베딩에 반영합니다. 청크 텍스트에는 설비·기간·에러코드를 자연어로 녹여 넣어 검색 정확도를 높입니다.

04유즈케이스

4개 기능 모두 History(UC1) 또는 Spec-check(UC2) 패턴 중 하나로 구현되며, Feature Registry로 관리됩니다.

History
PATTERN: history · 항상 RAG
입력
사용자 자연어 질의 + 필터(설비/기간/에러코드)
처리
하이브리드 검색 → LLM 판정/결론
데이터 소스
logs_raw / log_chunks (ETL → polling 임베딩)
Focal Curve
PATTERN: spec_check · 조건부 RAG
입력
curve 배열(data) + 스펙(spec) — inline 또는 DB/API 조회
처리
FocalCurveEvaluator가 range/sigma/DOF 결정론 계산 → OOS/근접 시만 RAG
출력
determination, margin_pct (+ OOS 시 원인가설·권고)
Final XY
PATTERN: spec_check · 조건부 RAG
입력
X/Y 포인트 집합(data) + 스펙(spec)
처리
FinalXYEvaluator가 mean±3σ 결정론 계산 → OOS/근접 시만 RAG
출력
determination, margin_pct (+ OOS 시 원인가설·권고)
ID Dump
PATTERN: root_cause · 항상 RAG
입력
에러 발생 로그 파싱 결과
처리
평가자 없음 — 과거 원인분석 이력(judgements)과 유사도 검색 → LLM 원인 추정
전제조건
엔지니어가 기록한 과거 원인 분석 시드 데이터 필요

06로드맵

PHASE 0

스펙 확정

logs_raw 실제 스키마, ASML API 응답 필드, 사내 LLM/임베딩 API 스펙(배치·rate limit·tool-calling 지원 여부) 확인

PHASE 1

UC1 임베딩 동기화

embedded_at 컬럼 기반 polling 워커 구축 및 검증

PHASE 2

UC1 History 서비스

하이브리드 검색 + LLM 판정 엔드포인트 구현

PHASE 3

Spec Evaluator 프레임 + Focal Curve / Final XY

결정론적 evaluator, feature_type 스키마 확장, 조건부 RAG 결합

PHASE 4

ID Dump

원인분석 시드 데이터 확보 → 유사사례 검색 기반 원인 추정 기능

PHASE 5

평가 · 튜닝

골든셋 기반 정확도 측정, 청킹/임계치/프롬프트 튜닝

확장(선택)

MCP 탐색 레이어

핵심 판정 안정화 이후, 엔지니어용 대화형 탐색 인터페이스로 별도 추가

07논의 필요 사항

부서 협의가 필요한 항목입니다.

Q

ASML API(data/spec) 및 logs_raw의 실제 필드명·스키마 확정

Q

Focal Curve / Final XY의 스펙 판정 기준 — range, sigma, DOF 윈도우 중 부서 표준 계산식 확인

Q

사내 Gemma4-260430 API의 tool-calling(function calling) 지원 여부 — MCP 탐색 레이어 도입 가능성 판단 기준

Q

BGE-M3/Gemma4-260430 API의 배치 처리 지원 여부, rate limit — 임베딩 백필 처리량 설계에 필요

Q

ID Dump 기능의 초기 정확도를 위한 과거 원인분석 시드 데이터 확보 방안 및 담당자

Q

margin_pct(스펙 근접 판단 임계치) 적정값 — 현재 10% 가정, 부서 경험치 반영 필요
