IMPLEMENTATION GUIDE · AS-BUILT

ASML 설비 로그 RAG 시스템
구현 가이드

asml-rag-overview.html이 구현 전 아키텍처 논의 자료였다면, 이 문서는 실제로 작성된 코드 기준으로 모듈이 서로 어떻게 참조되고, 요청이 어떤 경로로 흐르며, API와 LLM에 어떻게 질의하는지를 정리한 as-built 가이드입니다.

Phase 0 하네스 Phase 1 임베딩 동기화 Phase 2 UC1 History Phase 3 Spec Evaluator Phase 4 UC2 API 결합 Phase 5 평가·튜닝 Phase 6 기능 확장 Phase 7 MCP(선택)

00개요

두 유즈케이스가 하나의 RAG 코어(run_rag_judgement())를 공유합니다. UC1은 자연어 질의를 받아 항상 검색·판정을 수행하고, UC2는 결정론적 스펙 판정을 먼저 계산한 뒤 OUT_OF_SPEC이거나 스펙 여유가 부족할 때만 같은 RAG 코어를 호출합니다.

PRINCIPLE 01

판정과 설명의 분리

rag/spec_evaluator.py는 외부 의존성이 전혀 없는 순수 함수이며, LLM은 이미 계산된 판정 결과에 대한 설명만 생성합니다. 숫자를 재계산하지 않습니다.

PRINCIPLE 02

1개 RAG 코어 공유

UC1(routes_history.py)과 UC2(routes_spec_check.py)는 rag/core.py의 동일한 함수를 use_case/eval_id 인자만 다르게 호출합니다.

PRINCIPLE 03

메타데이터 필터 우선

hybrid_search()는 feature_type 필터 없이 전체 테이블에 벡터 유사도만으로 검색하는 것을 금지하며, 항상 구조화 필터를 먼저 적용합니다.

04UC2 호출 흐름 — /query/spec-check

판정은 항상 결정론적으로 계산·저장되고, LLM 설명은 OUT_OF_SPEC이거나 margin_pct가 임계치(기본 10%) 이하일 때만 조건부로 실행됩니다 (FR-2.3).

POST /query/spec-check

↓
asml_client.fetch_data_and_spec()
clients/asml_api_client.py · httpx+tenacity
↓ (data, spec)
evaluate_spec(data, spec)
rag/spec_evaluator.py · 순수 함수, LLM 미사용
↓ SpecResult(determination, margin_pct)
save_spec_evaluation()
db/repo.py → spec_evaluations · 항상 실행
↓ eval_id
margin_pct > 임계치 AND IN_SPEC
RAG 생략
determination/margin_pct만 응답
OUT_OF_SPEC OR margin_pct ≤ 임계치

use_case="spec_check", eval_id 연계
↓ (오른쪽 분기만) rag/core.py — UC1과 동일 코어
save_judgement()
eval_id로 spec_evaluations와 연계 저장
↓ SpecCheckResponse

margin_pct 계산식 rag/spec_evaluator.py

margin_pct = (1 − |value − center| / half_range) × 100 // center=(usl+lsl)/2, half_range=(usl−lsl)/2
// lsl == usl (스펙 폭 0)이면: value == center ? 100.0 : −100.0

05백그라운드 동기화

logs_raw.embedded_at IS NULL 커서 기반 polling으로, 중단 후 재시작해도 중복 임베딩 없이 이어서 처리됩니다.

APScheduler
EMBEDDING_SYNC_POLL_INTERVAL_SEC 주기
↓
SELECT logs_raw
WHERE embedded_at IS NULL LIMIT batch_size
↓
chunk_logs()
workers/chunker.py · 세션/에러 윈도우, 순수 함수
↓ (트랜잭션 밖) embedding_client.embed()
트랜잭션: INSERT log_chunks + UPDATE embedded_at
청크 밖 row도 함께 embedded_at 갱신 → 무한 재조회 방지

scripts/backfill_embeddings.py는 같은 run_embedding_sync_cycle()을 processed == 0이 될 때까지 반복 호출하는 1회성 스크립트입니다 — 로직을 복제하지 않습니다.

06API 호출해보기

로컬에서 uvicorn main:app --reload 실행 후 그대로 시도할 수 있습니다.

POST /query/history use_case = "history"

자유 형식 자연어 질의 + 선택적 필터(설비/기간) → 항상 검색 후 LLM 판정.

requestcurl
curl -X POST localhost:8000/query/history \
  -H "Content-Type: application/json" \
  -d '{
    "query": "EQ-01에서 최근 반복되는 overlay 정렬 실패 원인이 뭐야?",
    "equipment_id": "EQ-01",
    "top_k": 5
  }'
response200
{
  "judgement_id": 42,
  "conclusion": "...",
  "confidence": 0.82,
  "recommended_action": "...",
  "evidence_chunk_ids": [101, 104]
}
POST /query/spec-check use_case = "spec_check"

identifier(설비/파라미터)만 전달 — data+spec은 서버가 ASML API에서 직접 pull.

requestcurl
curl -X POST localhost:8000/query/spec-check \
  -H "Content-Type: application/json" \
  -d '{"equipment_id": "EQ-01", "parameter": "focus", "top_k": 5}'
response — OUT_OF_SPEC200
{
  "eval_id": 17, "determination": "OUT_OF_SPEC",
  "margin_pct": -12.5,
  "judgement_id": 8, "conclusion": "...",
  "confidence": 0.75, "recommended_action": "..."
}

여유가 충분하면(IN_SPEC, margin_pct > 임계치) judgement_id 이하 필드는 모두 null로 돌아옵니다 — RAG가 아예 호출되지 않았기 때문입니다.

07LLM에게 질문하기

UC1의 query는 진짜 자유 형식입니다. LLM은 rag/prompt.py의 시스템 프롬프트로 항상 아래 JSON 스키마만 반환하도록 강제되며, 제공된 근거(evidence) 밖 내용은 추측하지 않도록 지시받습니다.

일반 원인 질의

"EQ-03에서 지난주 반복된 E204 에러의 공통 원인이 뭐야?"

패턴 비교

"포커스 드리프트가 있었던 설비들의 공통점을 알려줘"

기간 필터 + 조치 이력

"최근 한 달 overlay 정렬 실패 사례의 조치 내역을 요약해줘"

period_start/period_end로 범위 제한 가능

근거 부족 케이스

"EQ-99에서 어제 무슨 일이 있었어?" (관련 청크가 없으면 confidence를 낮게 응답)

주의

UC2는 자유 질의를 받지 않습니다 — routes_spec_check.py의 _build_explanation_query()가 measured/lsl/usl/determination/margin_pct를 엮어 질의를 자동 생성하고, 조건을 만족할 때만 rag/core.py에 전달합니다.

08로컬 실행·디버그

  1. .env.example을 .env로 복사, EMBEDDING_PROVIDER/LLM_PROVIDER를 ollama로 두고 ollama pull bge-m3, ollama pull llama3
